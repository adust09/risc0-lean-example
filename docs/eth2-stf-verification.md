# ETH2 State Transition Function — zkVM Verification Results

## Conclusion

We implemented the Ethereum Consensus Layer (Beacon Chain) state transition function in Lean 4 and compared it against a Rust implementation on RISC Zero zkVM.

The Lean ETH2 STF runs correctly on the zkVM and produces byte-identical output to the Rust implementation. However, Init library initialization is mandatory. Skipping Init leaves closed terms such as `Array`, `String`, `ByteArray`, and `default` as NULL in the BSS segment, causing a NULL dereference crash. Unlike a sum function that operates solely on unboxed types like `UInt32`, a practical STF cannot avoid Init. Furthermore, `initialize_Init_Data` fails during Init initialization on the zkVM, so a workaround is needed: call it first to set the `_G_initialized` flag.

On the performance side, Lean's zkVM cycle count is 2.1x–2.4x that of Rust (depending on validator count), and the ELF size is 17.7x larger. The main sources of cycle overhead are the fixed Init cost (~15M cycles) and reference counting operations on persistent data structures.

## Init Skip Experiment Details

The no-Init configuration crashes with the following error.

```
Invalid trap address: 0x00000000, cause: LoadAccessFault(0x00000008)
```

In the C IR generated by the Lean compiler, `default` values, empty arrays `#[]`, literals like `ByteArray.mk #[0xFF]`, etc., are placed in the BSS segment as closed terms. `initialize_Guest()` initializes these at runtime, but without Init they all remain NULL, causing a NULL dereference on access.

To identify the root cause of the crash, we incrementally modified the C wrapper and performed a binary search.

| Test | Description | Result |
|--------|------|------|
| 1 | Init only, return static buffer | PASS (15.8M cycles) |
| 2 | Init + call `risc0_main(10)` | PASS |
| 3 | Init + `risc0_main_eth2(empty)` + access result | CRASH |
| 3b | Same as above, ignore result | PASS |
| 5 | Output return value as raw pointer | **return value = NULL** |
| 8 | Read memory at closed term address | **still NULL after Guest init** |
| 9 | Diagnose initialization steps | **`initialize_Init` fails** |
| 12 | Test Init submodules individually | **`initialize_Init_Data` fails** |
| 13 | Call Data first → Init → Guest | **all succeed** |
| 15 | Workaround + real data | **STF execution succeeds** |

The root cause is `initialize_Init_Data()`. The Init_Data initialization path calls libc file operations, but the zkVM's `shims.c` returns `-1` for all file operations. Meanwhile, `strerror(0)` returns "success" (since errno remains 0), so Init_Data interprets error code 0 as a failure and returns the error message `"success (error code: 0)"`.

The workaround is to call `initialize_Init_Data()` first. The call itself fails, but internally sets the `_G_initialized = true` flag. When `initialize_Init()` is called afterward, Init_Data is skipped as "already initialized," and the entire sequence succeeds.

```c
// methods/guest-eth2-init/risc0_lean.c
lean_initialize_runtime_module(lean_io_mk_world());  // (1) Runtime initialization
initialize_Init_Data(1, lean_io_mk_world());         // (2) Fails but sets _G_initialized=true
initialize_Init(1, lean_io_mk_world());              // (3) Skips Data and succeeds
initialize_Guest(1, lean_io_mk_world());             // (4) Initializes all closed terms
```

## Overhead Analysis

The Lean/Rust cycle count ratio increases from 2.1x at N=10 to 2.4x at N=100. There are three main contributing factors.

1. **Fixed Init cost (~15M cycles)** — Initialization of 392 modules. At N=10, this accounts for about 57% of total cycles and remains constant regardless of input size
2. **Persistent data structure cost** — Lean's `Array.set!` triggers a copy when the reference count is not 1. The impact grows with validator count, causing the ratio to increase from 2.1x to 2.4x between N=10 and N=100
3. **Reference counting operations** — RC increment/decrement during struct updates via `{ state with ... }`

The 17.7x ELF size difference is mainly due to static linking of the Init library. The breakdown is: Init library ~4.0 MB, Lean runtime ~1.0 MB, Guest code ~2.5 MB, libc/libstdc++ ~0.1 MB, totaling 6.6 MB. Rust uses only the zkVM runtime at 373 KB.

## Implementation Overview

The Lean STF is implemented across 19 files under `guest/Guest/Eth2/`. Type definitions conform to the Altair/Bellatrix spec (`Slot = UInt64`, `Gwei = UInt64`, `Root = ByteArray`, etc.). Epoch processing (12 sub-functions) and Block processing (header → randao → eth1_data → operations → sync_aggregate) are implemented in spec order. Cryptographic primitives (`hash_tree_root`, BLS verification) are all stubbed, and proposer selection is simplified to `slot % active_validator_count` (no RANDAO shuffle).

```
guest/Guest/Eth2/
  Types.lean, Constants.lean, Crypto.lean (stub)
  Containers.lean, Helpers.lean, Serialize.lean, Decode.lean
  Transition/
    StateTransition.lean        -- state_transition, process_slots
    Epoch.lean                  -- process_epoch (12 sub-functions)
    Block.lean                  -- process_block
    Block/{Header,Randao,Eth1Data,Operations,SyncAggregate}.lean
```

The entry point is exported to C FFI via `@[export risc0_main_eth2]` and called with a `ByteArray → ByteArray` interface. On success, it returns the serialized post-state BeaconState; on failure, it returns `0xFD` + a UTF-8 error message.

The FFI pipeline processes in the following order: Rust guest → C wrapper (Init_Data workaround + `initialize_Guest`) → Lean FFI → `Guest.lean` (decode → stateTransition → serialize). The guest crates are: `methods/guest-eth2-init/` (working configuration), `methods/guest-eth2-noinit/` (control group for Init skip experiment), and `methods/guest-rust-eth2/` (Pure Rust baseline).
