# ETH2 State Transition Function — Lean 4 x RISC Zero zkVM Unified Report

## Conclusion

We implemented the Ethereum Consensus Layer (Beacon Chain) state transition function in Lean 4 and compared it against a Rust implementation on RISC Zero zkVM.

**Direct execution approach (current):** The Lean ETH2 STF runs correctly on the zkVM and produces byte-identical output to the Rust implementation. However, Init library initialization is mandatory. Skipping Init leaves closed terms such as `Array`, `String`, `ByteArray`, and `default` as NULL in the BSS segment, causing a NULL dereference crash. Unlike a sum function that operates solely on unboxed types like `UInt32`, a practical STF cannot avoid Init. Furthermore, `initialize_Init_Data` fails during Init initialization on the zkVM, so a workaround is needed: call it first to set the `_G_initialized` flag.

On the performance side, Lean's zkVM cycle count is 2.0x–3.7x that of Rust (depending on validator count), and the ELF size is 17.7x larger. The main sources of cycle overhead are the fixed Init cost (~15M cycles) and reference counting operations on persistent data structures. The Lean/Rust ratio worsens as validator count increases (2.0x at N=1 → 3.7x at N=1000).

**IR trace verification approach:** We also evaluated an alternative approach that verifies Lean IR execution traces within the zkVM, but full-scope (entire ETH2) verification is not practical at this time. The barriers are: the high cost of reproducing IR execution semantics, dependency on host-specific functionality, and I/O cost of large-scale traces.

## Init Skip Experiment Details

The no-Init configuration crashes with the following error.

```
Invalid trap address: 0x00000000, cause: LoadAccessFault(0x00000008)
```

In the C IR generated by the Lean compiler, `default` values, empty arrays `#[]`, literals like `ByteArray.mk #[0xFF]`, etc., are placed in the BSS segment as closed terms. `initialize_Guest()` initializes these at runtime, but without Init they all remain NULL, causing a NULL dereference on access.

To identify the root cause of the crash, we incrementally modified the C wrapper and performed a binary search.

| Test | Description | Result |
|--------|------|------|
| 1 | Init only, return static buffer | PASS (15.8M cycles) |
| 2 | Init + call `risc0_main(10)` | PASS |
| 3 | Init + `risc0_main_eth2(empty)` + access result | CRASH |
| 3b | Same as above, ignore result | PASS |
| 5 | Output return value as raw pointer | **return value = NULL** |
| 8 | Read memory at closed term address | **still NULL after Guest init** |
| 9 | Diagnose initialization steps | **`initialize_Init` fails** |
| 12 | Test Init submodules individually | **`initialize_Init_Data` fails** |
| 13 | Call Data first → Init → Guest | **all succeed** |
| 15 | Workaround + real data | **STF execution succeeds** |

The root cause is `initialize_Init_Data()`. The Init_Data initialization path calls libc file operations, but the zkVM's `shims.c` returns `-1` for all file operations. Meanwhile, `strerror(0)` returns "success" (since errno remains 0), so Init_Data interprets error code 0 as a failure and returns the error message `"success (error code: 0)"`.

The workaround is to call `initialize_Init_Data()` first. The call itself fails, but internally sets the `_G_initialized = true` flag. When `initialize_Init()` is called afterward, Init_Data is skipped as "already initialized," and the entire sequence succeeds.

```c
// methods/guest-eth2-init/risc0_lean.c
lean_initialize_runtime_module(lean_io_mk_world());  // (1) Runtime initialization
initialize_Init_Data(1, lean_io_mk_world());         // (2) Fails but sets _G_initialized=true
initialize_Init(1, lean_io_mk_world());              // (3) Skips Data and succeeds
initialize_Guest(1, lean_io_mk_world());             // (4) Initializes all closed terms
```

## Overhead Analysis

The Lean/Rust cycle count ratio worsens with increasing validator count, from 2.0x at N=1 to 3.7x at N=1000. There are three main contributing factors.

1. **Fixed Init cost (~15M cycles)** — Initialization of 392 modules. At N=10, this accounts for about 57% of total cycles and remains constant regardless of input size
2. **Persistent data structure cost** — Lean's `Array.set!` triggers a copy when the reference count is not 1. The impact grows with validator count, causing the ratio to increase from 2.1x to 2.4x between N=10 and N=100
3. **Reference counting operations** — RC increment/decrement during struct updates via `{ state with ... }`

The 17.7x ELF size difference is mainly due to static linking of the Init library. The breakdown is: Init library ~4.0 MB, Lean runtime ~1.0 MB, Guest code ~2.5 MB, libc/libstdc++ ~0.1 MB, totaling 6.6 MB. Rust uses only the zkVM runtime at 373 KB.

### Why Validator Count Affects STF Cost

The ETH2 STF directly iterates over and updates the validator set, so validator count `N` directly determines computational cost.

Main factors:

1. **State decoding/encoding is proportional to N**
   - Processes variable-length arrays: `validators`, `balances`, participation flags, `inactivityScores`, etc.
   - Reference: `guest/Guest/Eth2/Serialize.lean`

2. **Proposer/active validator computation scans all N validators**
   - `getActiveValidatorIndices` performs a full scan of validators
   - Reference: `guest/Guest/Eth2/Helpers.lean`

3. **Each epoch processing sub-function has N-dependent loops**
   - rewards/penalties, inactivity, effective balance, registry updates, etc.
   - References:
     - `guest/Guest/Eth2/Transition/Epoch/RewardsAndPenalties.lean`
     - `guest/Guest/Eth2/Transition/Epoch/InactivityUpdates.lean`
     - `guest/Guest/Eth2/Transition/Epoch/EffectiveBalances.lean`
     - `guest/Guest/Eth2/Transition/Epoch/RegistryUpdates.lean`

Note: The benchmark input (slot 100 → 101) does not cross an epoch boundary, so decode/encode and block-side costs are dominant. Even so, the incremental cost from increasing N is clearly visible.

## IR Trace Verification Approach Evaluation

The current approach of compiling Lean 4 to C and executing it directly in the zkVM guest incurs high Init initialization costs with limited room for improvement. We therefore evaluated the practicality of an **alternative approach that verifies Lean IR execution traces within the zkVM** (referencing `ir_interpreter.cpp`), assuming an ETH2 state transition workload.

### Conclusion

**Full-scope (entire ETH2) IR trace verification is not practical at this time.**

Reasons:

1. **High cost of reproducing IR execution semantics**
   - Lean IR includes `inc/dec/del/reset/reuse/case/jmp` etc., requiring faithful reproduction of RC and heap updates
   - References:
     - IR instruction definitions: Lean `src/Lean/Compiler/IR/Basic.lean`
     - Reference implementation: `src/library/ir_interpreter.cpp`

2. **The reference implementation depends on host-specific functionality**
   - Symbol resolution via `dlsym/GetProcAddress` and other features that cannot be directly ported to the zkVM

3. **Cost of the trace input itself**
   - In the zkVM, proving cost is proportional to cycle count, and input/memory access also incurs cost
   - Feeding large traces results in significant I/O and paging overhead before any verification logic runs
   - Reference: RISC Zero Guest Optimization Guide

## Implementation Overview

The Lean STF is implemented across 19 files under `guest/Guest/Eth2/`. Type definitions conform to the Altair/Bellatrix spec (`Slot = UInt64`, `Gwei = UInt64`, `Root = ByteArray`, etc.). Epoch processing (12 sub-functions) and Block processing (header → randao → eth1_data → operations → sync_aggregate) are implemented in spec order. Cryptographic primitives (`hash_tree_root`, BLS verification) are all stubbed, and proposer selection is simplified to `slot % active_validator_count` (no RANDAO shuffle).

```
guest/Guest/Eth2/
  Types.lean, Constants.lean, Crypto.lean (stub)
  Containers.lean, Helpers.lean, Serialize.lean, Decode.lean
  Transition/
    StateTransition.lean        -- state_transition, process_slots
    Epoch.lean                  -- process_epoch (12 sub-functions)
    Block.lean                  -- process_block
    Block/{Header,Randao,Eth1Data,Operations,SyncAggregate}.lean
```

The entry point is exported to C FFI via `@[export risc0_main_eth2]` and called with a `ByteArray → ByteArray` interface. On success, it returns the serialized post-state BeaconState; on failure, it returns `0xFD` + a UTF-8 error message.

The FFI pipeline processes in the following order: Rust guest → C wrapper (Init_Data workaround + `initialize_Guest`) → Lean FFI → `Guest.lean` (decode → stateTransition → serialize). The guest crates are: `methods/guest-eth2-init/` (working configuration), `methods/guest-eth2-noinit/` (control group for Init skip experiment), and `methods/guest-rust-eth2/` (Pure Rust baseline).

## Future Work and Recommendations

### Direct Execution Approach — Open Items

- Implement cryptographic primitives (`hash_tree_root`, BLS verification)
- RANDAO-based proposer selection
- Test cases that cross epoch boundaries
- Measurements with larger validator sets (1,000+)
- Investigation of Init fixed cost reduction (excluding unnecessary modules, etc.)

### Recommended Approach

1. **Maintain Rust guest as the production path for now** — Prioritize minimizing proving cost
2. **Use Lean as the specification source + differential verification** — Continue output-matching tests between the Lean and Rust implementations
3. **Evaluate IR trace approach with a limited PoC in stages** — Restrict scope to partial functions such as `processSlots`, implement the verifier with a minimal opcode set only. Establish Go/No-Go criteria first (e.g., cycles/trace size upper bounds)
4. **Abandon full ETH2 deployment if criteria are not met** — Set a technical exit line early
