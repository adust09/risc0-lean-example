# Lean vs Rust zkVM Performance Comparison

Comparison of zkVM cycle counts (= proving cost) for three guest implementations of the same algorithm on RISC Zero zkVM.

The target computation is a recursive `sum` function. A 16-bit mask ensures identical output across all implementations.

```
sum(n) = if n == 0 then 0 else (n + sum(n - 1)) &&& 0xFFFF
```

| Implementation | Language | Type | FFI | Init Initialization |
|------|------|-----|-----|-------------|
| **Lean (UInt32)** | Lean 4 | `UInt32` (machine integer) | `uint32_t` direct | None |
| **Lean (Nat)** | Lean 4 | `Nat` (heap-allocated) | `ByteArray` marshalling | Yes (392 modules) |
| **Rust** | Rust | `u32` (machine integer) | None | None |

Trade-offs for each implementation:

- **Lean (UInt32)**: Cycle efficiency is comparable to Rust. However, since Init is not initialized, Lean standard features such as `String`, `List`, `Array`, `IO`, `Nat`, etc. are unavailable. Limited to unboxed types like `UInt8`–`UInt64`, `Bool`, etc.
- **Lean (Nat)**: Full access to Lean's standard library. However, Init initialization incurs a fixed cost of ~4.1M cycles, and each `Nat` operation requires heap allocation and reference counting.
- **Rust**: Baseline. Only the zkVM runtime with no additional overhead.

Build pipeline:

```
Lean:  Lean 4 → lake build → C IR → CMake (riscv32-gcc) → libGuest.a → Rust FFI → zkVM ELF
Rust:  Rust → cargo build (risc0-zkvm) → zkVM ELF
```

## Analysis

**Lean (UInt32) Cycle Efficiency** — Lean's `UInt32` compiles to unboxed machine integers. The generated C IR is structurally equivalent to Rust, with no heap allocation or reference counting.

C IR generated by the Lean compiler (`guest_build/risc0_ir/Guest/Basic.c`):

```c
LEAN_EXPORT uint32_t l_sum(uint32_t x_1) {
  uint32_t x_2; uint8_t x_3;
  x_2 = 0;
  x_3 = lean_uint32_dec_eq(x_1, x_2);
  if (x_3 == 0) {
    uint32_t x_4; uint32_t x_5; uint32_t x_6; uint32_t x_7; uint32_t x_8; uint32_t x_9;
    x_4 = 1;
    x_5 = lean_uint32_sub(x_1, x_4);
    x_6 = l_sum(x_5);
    x_7 = lean_uint32_add(x_1, x_6);
    x_8 = 65535;
    x_9 = lean_uint32_land(x_7, x_8);
    return x_9;
  } else {
    return x_2;
  }
}
```

Per-recursion cycle cost (derived from the difference between N=10 and N=10,000): Lean (UInt32) ~ 15.0, Rust ~ 16.0. Lean is approximately 6% more efficient, with the ratio shifting from 0.96x to 0.94x as N increases.

**Lean (Nat) Fixed Cost** — At N=10, 4,119,771 cycles; at N=100, 4,124,252 cycles — a fixed cost of ~4.1M cycles is observed regardless of input size. This is caused by `initialize_Init()` initializing 392 modules, which allocates static variables on the heap at runtime startup. Additionally, `Nat` is a boxed object requiring heap allocation, with a per-recursion cost of ~50 cycles (approximately 3x Rust's ~16).

**Wall-Clock Time Discrepancy** — All implementations show a discrepancy between cycle count and wall-clock time. Wall-clock time includes host-side ELF loading and setup time, which is independent of in-guest execution cycles. Since zkVM proving cost is proportional to cycle count, cycle count — not wall-clock time — is the meaningful cost metric.

**Init Skip Mechanism** — The Lean (UInt32) implementation's C wrapper (`methods/guest/risc0_lean.c`) calls `risc0_main` directly. The generated C IR contains `initialize_Guest()` which calls `initialize_Init()`, but since this function is never invoked, the Init initialization code is not executed. `libInit.a` is still included in the ELF due to linker dependency resolution (contributing to the 5.6x ELF size difference).

## Reproduction Steps

```bash
export RISC0_TOOLCHAIN_PATH="$HOME/.risc0/toolchains/v2024.1.5-cpp-aarch64-apple-darwin/riscv32im-osx-arm64"
export LEAN_RISC0_PATH="$HOME/.lean-risc0"

just clean && just build
target/release/host 100   # → 5050
just bench-execute
```
